# 实装 CANN 的 ACLNN 单算子缓存容量

CANN v9.1.0 的 `OpExecCacheManager` 按线程建立，构造时取得缓存上限；`K_CACHE_LIMIT` 是 10,000。生产编译路径以此为默认值，对提供的数字解析后应用上限。CANN 9.1.X 官方文档也给出每线程默认 10,000 个 Host 单算子缓存项。这是可容纳的条目数；实际占用、触发驱逐的次数、命中率和内存开销还需要各自的观测。[v9.1.0 常量](https://github.com/hicann/opbase/blob/0e247b8c759c48ae42fda6c6f2bd5daab323be0f/include/nnopbase/opdev/op_cache.h#L36) · [线程级 manager](https://github.com/hicann/opbase/blob/0e247b8c759c48ae42fda6c6f2bd5daab323be0f/src/nnopbase/common/utils/op_cache.cpp#L88) · [构造函数](https://github.com/hicann/opbase/blob/0e247b8c759c48ae42fda6c6f2bd5daab323be0f/src/nnopbase/common/utils/op_cache.cpp#L1272) · [容量读取实现](https://github.com/hicann/opbase/blob/0e247b8c759c48ae42fda6c6f2bd5daab323be0f/src/nnopbase/common/utils/op_cache.cpp#L1357) · [CANN 9.1.X 文档](https://www.hiascend.com/en-sg/document/detail/en/CANNCommunityEdition/910/maintenref/envvar/envref_07_0031.html)

host88 训练容器实装 `libnnopbase.so` 的 SHA-256 为 `308dda461704a6e5f70de6e0eac4495e9829b9cec3328563b75a5b382c6e438b`。用宿主侧只读文件检查实装二进制，其构造函数于 0x178a90 调用 `GetCacheSizeLimit`。该函数在平台入口存在时先查 `mmSysGetEnv(2000)`；返回空或入口不存在时，从 `MM_ENV_ACLNN_CACHE_LIMIT` 名称跳过 `MM_ENV_` 前缀，查进程 `getenv("ACLNN_CACHE_LIMIT")`。两者均无值时 0x176054 取 `0x2710` 并作为 10,000 返回。平台 accessor 先被调用，不能据此推断它有独立于进程环境的外部配置。当前训练容器 Docker Config.Env 中没有这个变量，正式训练腿仍以 worker 的实际环境收据为准。[实装反汇编及两次取值](cache-limit-verified.txt)

同一镜像的两个全新、只读、无 NPU runc 进程中，分别以未设置和显式 65,536 启动。前者的 `mmSysGetEnv(2000)` 返回 null，实际 `GetCacheSizeLimit` 返回 10,000，后者分别返回字符串 65536 和数值 65,536。两次都借用并释放真实线程的 manager。由此可写“当前同镜像缺省为 10,000，显式设置为 65,536 时容量约为缺省的 6.55 倍”；当前资料没有在每个训练 worker 内直接读取其 manager 的容量或实际命中数。[探针](cache_limit.py) · [无卡执行与二进制核对命令](cache-limit.sh)
