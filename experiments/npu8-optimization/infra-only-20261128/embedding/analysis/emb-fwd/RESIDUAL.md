**与已有路径的关系**

- **InplaceCopy 和 D04。** 流 44 每步有 1,052 个单 SDMA copy，对应后继空档 57.29 / 54.54 ms。流 47 上 1,060 个 SDMA 对应 53.21 / 50.64 ms，另有 1,092 个 Cast 对应 29.21 / 25.69 ms。D04 的直接 SDMA 守卫需要源块分配流、地址类型和 allocator 可记录性等条件，当前 trace 缺逐笔分配与别名信息。Cast 的 workspace 交集仅 0.02 / 0.01 ms，ACL 返回后占 17.07 / 23.59 ms。要识别可以安全省掉 dtype 转换的另一代码路径，还需每笔输入输出 dtype、别名及消费使用证据。
- **Divs。** 双向 embedding 的 B 腿保留原 Divs。大量 BroadcastTo 与这次单独验证的 op-plugin 紧凑广播候选使用相同算子与核序列。这里未叠加 Divs，当前两步可定位剩余重复工作。组合的增量收益需要直接配对。
- **D01、D03 与队列通知。** 此 B 腿已启用 D01 大缓存。两条 embedding 路径合计与 workspace 相交 1.053 / 0.603 ms，可见 API 区间中剩余重叠很小。D03 针对权重回写的 CPU 视图构造，上表的每步内部后继设备工作不直接测量它，跨步尾部空档也未计入排名。全部已关联请求与可见队列等待的交集为 18.466 / 12.460 ms。当前时间线缺少写指针发布和 eventfd 等待者状态，无法将这些重叠量归给某次 queue 唤醒。

**流 44 相邻 D2D 提交**

逐个匹配流 44 的单 SDMA 工作、`aclnnInplaceCopy` queue ID 及真实同线程 dequeue 顺序，中间出现任何其他 dequeue 便结束当前连续组。两步各得到唯一连续组，长度均为 1,052。在后项 enqueue 标记已结束、前项 dequeue 标记尚未开始时，第 4 步有 9 对相邻项满足条件，第 5 步为 0。按第一项 dequeue 开始时已就绪的后续项贪心分组，组长上限 64。第 4 步得到 1,043 个单项和 3 个三项组，最多节省 6/1,052 次提交。第 5 步全为单项。首尾标记是可见发布边界。具体地址是否相邻、源宿生命周期与同步依赖仍需额外信息。旧路径两步均得到 0，本次可见余量出现在第 4 步。[复算程序](../../residual.py) · [逐步结果](residual.json)
