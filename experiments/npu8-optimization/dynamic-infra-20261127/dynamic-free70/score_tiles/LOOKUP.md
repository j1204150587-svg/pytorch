# 动态 attention score 查表的 BF16 索引

原生核和 PR 计划提交共用的第一版 Triton 实现未通过 66 例逐位检查。实机用独立算子分别导出乘 0.25 后的 BF16 值、三个整数键、表值和最终 score。输入来自真实投影的 QK 乘法，覆盖 [1,13]、[2,14]、[4,31]，另用 [1,13] 做了一次 CPU 往返的输入对照。宿主端按真实 BF16 字重建每个期望索引，再从同一 NPU 生成的 SiLU 表逐项核对。

在三个形状上，目标编译器生成的 `bf16 → bitcast uint16 → int32` 实际分别有 323、774、7,715 个整数键与原 16 位模式不符。[1,13] 的第二个元素应为 49,071，实机写出 −16,465。输入缩放值逐位相同。改用 `bitcast int16 → int32 → & 65535`，以及通过 FP32 高 16 位构造索引，四组检查的所有键均准确。逐项验证的查表值和最终前向 score 也全部相同。完整 attention 反向和训练按独立实验记录。[实机结果](lookup-1037.json) · [逐元素诊断](lookup_probe.py) · [修正后的两个核](kernels_v3.py)

诊断窗口内按独立芯片记录核对到 4 个有效样本，采样到的设备进程均在训练容器中。本次运行的诊断源码、JSON 和卡前后快照分别与归档包一致。[原始实机包](../score-lookup-1037.tgz) · [独立芯片记录](../chip4-0-1036-1043.jsonl)
