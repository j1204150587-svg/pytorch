# 动态 BF16 RMS 前向查表

九处 RMSNorm 在每步的真实 [B,L,64] 上执行平方、均值、加 epsilon、rsqrt 和两次乘法。此前完整 Triton 复写在正常值的 rsqrt 以及小方差附近的加 epsilon 出现首个差异。本轮在目标设备用原生 BF16 `(mean + 1e-6).rsqrt()` 为 65,536 种 BF16 编码一次建表；Triton 按 BF16 原舍入边界得到均值，取原始编码查表，保留原顺序的两次乘法。A/B 共用带两条 x 梯度边的原生 BF16 反向。仅接受连续 BF16 布局与相同设备，其他 epsilon 走原生前向，异流首次使用时等待构表完成事件。[查表与反向](lut_rms.py) · [融合前向](lut_kernel.py) · [原生操作](rms_lut_parts.cpp)

逻辑 NPU 8 上，60 个合成形状覆盖 80 个输入样例，前向值、输入梯度和权重梯度逐位一致，A/B 各四个完整 HSTUBlock 的输出和七项梯度也均相同。测试包括零、负数、极值、次正规数、Inf 和 NaN 位型。两种大表布局的全部 65,536 位型吻合，四个小形状的抽样查表亦通过。0、−1e−6、1e−4 三种 epsilon 各回退一次，异流等待一次，各自逐位一致。一次冷建表 Host 为 20.635 ms，含设备同步 20.764 ms；表本身 131,072 字节，allocator 实际净增 131,584 字节。[NPU 原始记录](npu-gate.json) · [测试和复算](micro.py)

| 单个 RMS 前反向同步窗 | 原生前向，μs/次 | LUT 前向，μs/次 | 耗时变化 |
|---|---:|---:|---:|
| A/B | 495.12 | 611.01 | +23.41% |
| B/A | 496.65 | 612.36 | +23.30% |

每个窗口含 96 次完整 RMS 前反向，轮流使用 [1,19]、[2,14]、[2,22]、[4,31]。原生 Triton launcher 路径四轮均慢，尚无该路径的整步正收益。独立 forward-only 探针可以分别计时六个原生操作、同一 LUT Triton JIT、同一 LUT 的 PR 下发计划，并在预分配输出后单测后一对。Level1 的每个 shape/route/repeat 有独立的 dispatch 及同步边界，便于复核实际设备提交。[前向测量入口](forward_probe.py) · [Level1 复算](forward_trace.py)

同一本机 CPU 试验的 80 个输入只有 11 个完全一致。原生 CPU rsqrt 的向量主循环和标量尾部对某些位型采用不同舍入。该行为可阻止 CPU 开启查表，设备结论以上述实机门为准。[CPU 原始结果](cpu.json)

## 原生和 stock Triton 前向的 Level1 归因

关闭 profiler 后四个动态窗口的原生前向为 60.77–61.97 μs/次，stock LUT 为 120.76–124.05 μs/次。单独开启 Level1，对每种形状和路径采三次，逐次在前向结束后同步。四个形状均实际从六笔设备工作减少为一笔。表内是各形状的三次中位数，单位 μs。

| [B,L] | 入口至首次 enqueue，原生 / LUT | 入口至首笔设备工作，原生 / LUT | 有效设备工作并集，原生 / LUT |
|---|---:|---:|---:|
| [1,19] | 33.09 / 189.26 | 48.87 / 215.82 | 27.14 / 4.36 |
| [2,14] | 37.73 / 186.35 | 53.27 / 207.39 | 18.74 / 4.14 |
| [2,22] | 32.93 / 187.76 | 48.98 / 209.76 | 19.82 / 4.88 |
| [4,31] | 32.48 / 187.06 | 47.83 / 208.72 | 35.24 / 7.70 |

两条路径的 consumer 区间中位都在 8.83–10.68 μs。额外开销集中在生产者发起第一笔入队之前。该次计划路径守卫要求生成的 launcher 源文件仅有一处物理 grid cap，实际 launcher 的两个入口使用相同 cap，因此该轮只测出原生和 stock LUT。[未剖析逐笔时延和 ABI](forward-npu.json) · [24 个 Level1 窗口逐笔结果](forward-level1-ns.json)

## 同一个 LUT 核的七指针 PR 计划

第二轮按原 launcher 的两个入口验证相同的物理上限 40，三维逻辑 grid 保持原值。七个 tensor 参数包括权重、查表和三份输出，最后的 debug 参数在 `DEBUG=False` 时使用输入地址。原始代码只读同一张表，两个物理流、四种形状都逐位核对 y、inv、z。计划返回 544/544 次，其中 272 次实际走 physical-cap 入口。无 profiler 同步窗口如下，单位 μs/次，每窗口 64 次，包含获取表和申请输出的开销。

| 顺序 | 原生六算子 | 原 Triton LUT | 同核 PR 计划 | 计划相对原生节省 |
|---|---:|---:|---:|---:|
| 原生 / Triton / 计划 | 62.97 | 126.10 | 62.17 | 0.80 |
| 计划 / Triton / 原生 | 62.56 | 125.12 | 60.85 | 1.71 |
| 原生 / Triton / 计划 | 62.57 | 124.93 | 61.57 | 1.00 |
| 计划 / Triton / 原生 | 63.09 | 124.29 | 60.96 | 2.13 |

单独复用预分配的输入输出时，同核下发的四轮同步均值从 56.96–58.50 缩至 16.64–17.02 μs。Level1 的 12/12 个形状与重复配对均验证相同物理流、相同工作名称/类型和一笔设备提交。stock → plan 的 producer 首次 enqueue 前中位从 189.89–197.08 降至 99.50–113.58 μs，consumer 从 9.23–10.52 降至 6.47–6.88 μs，核时从 2.78–8.16 变为 3.00–8.22 μs。PR 计划的 consumer 内部没有可分别计时的 ACL launch 标记。[原始未剖析样本、真实 ABI 和各路径计数](forward-plan-npu.json) · [36 个 Level1 窗口和物理流任务](forward-level1-plan.json)
